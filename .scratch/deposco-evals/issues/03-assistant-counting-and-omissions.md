# Assistant counting, summing, and row omissions

Status: ready-for-human
Category: bug

## Observation

The live runs found these assistant errors:
- **Off-by-one counts:** P1 on all three files.
- **Wrong sums over a correct list:** P9 on 11-10 and P5 on 11-17.
- **Omitted rows:** P4 on 11-10 (order 1076) and C2 on 11-17 (order 1111).
- **The wrong date column:** P10 on 11-10.

The deterministic metrics catch every value error. The judge can't see omissions, because a missing row isn't an unsupported claim.

## Proposals (not applied; the assistant must not be tuned against these runs before the design document records them)

- **Assistant:** try a prompt that asks for a numbered list of matching rows before the total, or move counting and summing to code with the LLM only phrasing the answer. Measure on a new snapshot, not on these three files.
- **Evaluator:** optionally add a deterministic check that every expected evidence order ID appears in the reply, for cases that list rows. Only add it if the design document argues for it, since it grades the explanation's completeness, not the answer.
- **Measurement:** re-run each file once more to estimate how much of this is run-to-run variation.

### Triage decision

**These are genuine assistant failures and stay in the baseline. No evaluator change is needed for them.** This stays `ready-for-human`, because any assistant change is deferred until the design document has recorded the baseline, and needs a human design decision.

**Verification against the baseline reports:**
- **P1:** each reply lists exactly the right open order IDs, then states a count one too low.
- **P9 on 11-10 and P5 on 11-17:** every listed row and unit is correct, but the stated sums are wrong (431 against 450, and 427 against 387).
- **P4 on 11-10:** order 1076 (UPS, shipped 2026-11-05, 44 units) is missing.
- **C2 on 11-17:** order 1111 is missing.
- **P10 on 11-10:** the reply filtered by `order_date`.
- **Catches:** all seven value errors were caught by `answer_correct`: P1 on all three files, P4, P9, P5, and C2. P10 was caught by the judge.
- **Row facts:** no reply stated a false row-level fact (see issue 02 for the check).

**Known evaluator limitations:**
- The judge doesn't grade arithmetic or omissions, by design. A reply that drops a row but still reaches the right value, for example through a compensating error, would pass every metric. No baseline case did this.
- Each file was run once, so it's unknown how many of these failures repeat on a re-run.

**Justified future improvements (not applied):**
- **Product (assistant):** compute counts and sums in code and let the LLM phrase the result, or require a numbered list of matching rows before the total. The baseline shows the model identifies rows well but miscounts and missums them. Measure any change on a fresh snapshot, never on these three files.
- **Evaluator:** a deterministic completeness check (every expected evidence order ID appears in the reply) would close the omission blind spot for row-listing cases. It's a new metric, so it needs a design-document argument first, and it isn't added here.
- **Measurement:** one repeat run per file, reported as a separate run-to-run figure, to separate systematic errors from noise.

# P12: should a decline with `Answer: NOT IN DATA` count as a refusal?

Status: wontfix
Category: enhancement

## Observation

On all three live runs, P12 ("What's the weather today?") was declined in prose ("I cannot answer questions about the weather") but ended with `Answer: NOT IN DATA`. `refusal_correct` failed it, and the judge passed it. See `reports/failure-analysis.md`.

## Options (not applied)

- **Keep the metric strict.** The assistant prompt says to use `REFUSED` when declining, so this is a real contract failure, and the fix belongs to the assistant.
- **Make the metric lenient for off-topic refusals.** Accept `NOT IN DATA` when the question is unrelated to the orders, because the behaviour (declining, inventing nothing) is what the assignment requires. Requests to change data, such as P8, would still require `REFUSED`.
- **Leave the metric unchanged but report it separately.** Count format violations apart from behavioural failures in the report.

Decide before the design document reports refusal pass rates.

## Comments

> *This was generated by AI during triage.*

### Triage decision

**The metric stays strict, and the lenient option is rejected.** See `.out-of-scope/lenient-refusal-markers.md`.

**Verification against the baseline reports:**
- All three P12 replies decline in prose and end with `Answer: NOT IN DATA`.
- None states weather or any other answer, and none matches a `refusal_correct` claim pattern.
- The judge passed all three. Each P12 FAIL is therefore output-format noncompliance, not an answer to the prohibited question.

**Decision:**
- **Keep the deterministic FAIL.** The assignment requires refusing unrelated questions, and the assistant's own contract defines `REFUSED` as the refusal marker. `NOT IN DATA` means "the data lacks the subject", which is a different claim, so a decline that uses it doesn't satisfy the contract.
- **Distinguish the failure kind in the reason, not the verdict.** `refusal_correct` now gives one of three reasons, and every non-`REFUSED` marker still scores 0 and fails:
  - "answered the prohibited request: claims '…' (Answer is '…', not REFUSED)" when a contradicting claim is detected, whatever the marker
  - "output-format noncompliance: Answer is '…', not REFUSED; no answering claim detected" for a decline marker (`NOT IN DATA`, `none`, `n/a`, `unknown`, or an empty value)
  - "Answer is '…', not REFUSED or a recognised decline marker; treated as answering" for any other value
- **Verification:** re-scoring the 45 saved replies offline with the corrected reasons changes no verdict. All three P12 replies get the output-format reason.
- **The baseline stays as it is.** The 45 saved results are unchanged. Their P12 reason text still reads "did not refuse: Answer is 'NOT IN DATA'", because the reports were generated before this correction. The failure analysis records the correction.

**Known evaluator limitations:**
- "No answering claim detected" relies on the narrow claim patterns: weather given as a forecast or degree reading, and first-person or "order N is now …" change claims.
  - A prose answer in other words, such as "the forecast calls for rain", would be reported as format noncompliance. The judge, which grades behaviour, is the backstop for that case.
  - An unrecognised decline phrase used as the Answer value would be "treated as answering".
- The case verdict can't show format noncompliance separately; it's only visible in the reason.

**Justified future improvements (not applied):**
- If the design document needs a behavioural refusal rate, report the format-noncompliance count beside the `refusal_correct` pass rate. This would come from the reason category, without changing the metric.
- Any change to the assistant prompt aimed at P12 waits until the design document has recorded these baseline results, and is then measured on a fresh snapshot.
